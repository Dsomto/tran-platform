Track 1 · SOC Analysis

SOC Analysis: turning raw logs into proven incidents

You worked a live-style incident as a blue-team analyst. Five raw log sources landed on your desk, each arriving in three different formats, riddled with a few deliberately broken rows and one source whose clock was wrong. Your job was to build one trustworthy timeline out of all of it, prove three planted attack campaigns from that timeline, and correctly judge 96 flagged activities as either routine or worth escalating. This section walks through exactly what a strong answer looked like, where most people lost marks, and a lab you can rerun end to end.

Read it once for the shape of the whole thing, then read it a second time with your own submission open beside it. The single most useful question you can ask is: for every claim I made, did a delivered file actually prove it? That is the question the rubric asks, and it is the one that separated the strong submissions from the polished-but-empty ones.

CriterionMaxWhat earned the marks

Pipeline and data quality (20). The dividing line here was runnable versus described. High answers shipped a normalizer you could execute against the pack and watch produce the outputs. Low answers described the pipeline in prose, or shipped code that did not run as delivered. The examiner did not award these points for a report that merely listed the eleven behaviours (below). The proof lived in the generated database, the reconciliation file, and a second clean run, not in the write-up.

Campaign accuracy (30), the largest single block. The gap between high and low was whether each link in a campaign was proven from two independent raw sources or asserted from one keyword hit. A submission that found the sprayed IP and stopped scored far below one that walked the ordered chain (many failures over time, then a success on the sprayed account, then the follow-on action) with each step backed by a distinct source. Three generic SQL queries earned very little here, however clean the SQL.

Evidence and correlation (25). This measured whether all 96 review candidates were actually adjudicated, each to a real locator, rather than summarised. Writing the aggregate "80 and 16" in prose scored near the bottom of this band. Itemising every unique REVIEW-#### id with a structured verdict and a pointer to the evidence scored at the top.

False-positive restraint (15). This rewarded judgment. Escalating everything to look thorough is easy and wrong. The strong answers correctly left the 80 approved, in-window, change-covered activities as benign and escalated only the 16 that genuinely broke a check. Over-escalation and under-escalation both cost marks here.

Communication and reproducibility (10). The smallest block, but it is where a good submission proved it was trustworthy. A reviewer who could take your README, run your build, and land on the same hashes gave full marks. A submission with no manifest, no attestation, or a build that only ran on the author's laptop lost them.

1.2The data model: five sources, three schemas each

You received five raw sources. Each source shipped in three schema versions, because in real life log formats drift as tools get upgraded, and a normalizer has to survive that drift. Every version of a source had to normalize to one canonical event contract, so that downstream correlation never had to care which format a row originally came in.

SourceSchema versionsNormalizes to
AuthenticationAUTH-V1, AUTH-V2, AUTH-V3One canonical auth event (actor, source IP, host, outcome, UTC time)
WebWEB-V1, WEB-V2, WEB-V3web_request (client IP, request id, host, bytes, UTC time)
DNSDNS-V1, DNS-V2, DNS-V3dns_query (client, query name, response, UTC time)
FirewallFIREWALL-V1, FIREWALL-V2, FIREWALL-V3network_deny (source, destination, port, action, UTC time)
EndpointENDPOINT-V1, ENDPOINT-V2, ENDPOINT-V3One canonical endpoint event (host, actor, process or file, device, UTC time)

The point of three versions is that a field can move, get renamed, or change type between versions, but the meaning is stable. Your adapter for AUTH-V1 and your adapter for AUTH-V3 read different-looking rows and emit the same canonical shape. Correlation then joins on canonical fields (actor, IP, host, object, time) and never has to branch on format again. Here is a small, clearly fictional illustration of two auth rows arriving in two different schema versions and normalizing to the same event.

One event, two schemas, one canonical result (illustrative)

// AUTH-V1 raw row (flat, epoch seconds, verb "result")
{ "u": "amina@example.invalid", "src": "198.51.100.124",
  "host": "amina-ad4", "result": "fail", "ts": 1752393600 }

// AUTH-V3 raw row (nested, ISO time, verb "status")
{ "actor": { "name": "EXAMPLE\\amina" },
  "network": { "source_ip": "198.51.100.124" },
  "asset": "amina-ad4", "status": "failure",
  "time": "2026-07-13T08:00:00Z" }

// BOTH normalize to the same canonical auth event:
{ "actor": "amina", "source_ip": "198.51.100.124",
  "host": "amina-ad4", "outcome": "fail",
  "ts_utc": "2026-07-13T08:00:00Z",
  "source_file": "auth-v1.log", "row": 42 }
Notice three things the normalizer had to do even in this tiny example: reconcile two different actor spellings to amina, map two different outcome verbs (fail and failure) to one canonical value, and carry the original file and row number so any downstream claim can be traced back. That last part, provenance, is what makes an evidence locator possible later.

1.3The eleven normalizer behaviours, and why each one matters

A correct normalizer showed eleven distinct behaviours. Each one exists for a reason, and skipping any of them quietly corrupts the timeline or the reconciliation. Work through these with your own code open.

  1. Parse all three schema versions per source through explicit adapters (or equivalent typed logic). Why it matters: if you only handle the version you happened to open first, rows in the other two versions are silently dropped, and dropped rows mean missing edges in a campaign.
  2. Preserve source filename and row locator on every event. Why it matters: an evidence locator is not optional decoration. It is the difference between "trust me, there was a login" and "auth-v2.log line 118." Every one of your 96 verdicts and every campaign edge depends on this.
  3. Quarantine malformed JSON as invalid_json. Why it matters: a broken row must not crash the run and must not be silently discarded. It goes to quarantine with a reason so the counts still reconcile.
  4. Quarantine a row with no usable timestamp as missing_time. Why it matters: an event with no time cannot be placed on a timeline or correlated across sources, so it is set aside with a named reason rather than guessed at.
  5. Detect unsupported schema variants instead of dropping them silently. Why it matters: if a fourth, unknown format appears, the safe behaviour is to flag it, not to pretend it parsed. Silent loss here is invisible and dangerous.
  6. Apply the endpoint clock correction of minus 3,900 seconds. Why it matters: this is the trap that broke the most timelines. See the worked example below.
  7. Resolve identity aliases to one canonical identity. Why it matters: amina@example.invalid and EXAMPLE\amina are the same person as amina. If you treat them as three actors, the spray-then-success chain never joins up.
  8. Remove or account for duplicates without losing provenance. Why it matters: the same event can appear in two feeds. You dedup to one canonical event, but you keep a record of both origins so counts still reconcile and so you can cite either source.
  9. Keep stable ordering for equal timestamps. Why it matters: when two events share a timestamp, a deterministic tiebreak (for example by source file then row) means two runs produce the same ordered timeline, which is what makes hashes match.
  10. Reconcile accepted, quarantined, and duplicate counts to the source manifest. Why it matters: this is your proof that nothing was lost. See the reconciliation identity below.
  11. Produce identical output hashes across two clean runs. Why it matters: determinism is how a reviewer confirms your result is real and not accidental. Non-deterministic output (unstable ordering, unsorted maps, timestamps of the run itself) fails this.

Worked micro-example: the endpoint clock fix

The endpoint source ran 65 minutes fast, which is 3,900 seconds. Every endpoint event needs minus 3,900 seconds applied before it joins the timeline. 
# before correction (endpoint clock is 65 minutes fast)
endpoint event stamped  2026-07-13T09:05:00Z
# apply the correction: minus 3900 seconds
09:05:00Z  -  3900s  =  08:00:00Z
# after correction
endpoint true event time   2026-07-13T08:00:00Z
Why this matters so much: the campaigns cross from web or auth into endpoint activity. If your endpoint events sit an hour late, the endpoint step of a campaign lands after the DNS or web step it was supposed to follow, the ordered chain breaks, and the correlation looks like noise. Miss this one correction and two of the three campaigns quietly fall apart even though every other behaviour is perfect.

Worked micro-example: quarantine, not silent loss

// a row that is not valid JSON at all
{ "actor": "svc-backup", "outcome": "ok",   <- trailing comma, unterminated
// -> quarantine.csv: reason=invalid_json, source_file=..., row=...

// a row that parses but has no usable time
{ "actor": "amina", "source_ip": "198.51.100.124", "host": "amina-ad4" }
// -> quarantine.csv: reason=missing_time, source_file=..., row=...
Both rows leave the accepted stream, but neither vanishes. Each lands in quarantine.csv with a named reason and its locator, which is exactly what lets the reconciliation add back up.

Worked micro-example: alias resolution and dedup with provenance

# three spellings, one person
amina@example.invalid  ->  amina
EXAMPLE\amina          ->  amina
amina                  ->  amina

# same event seen in two feeds -> one canonical event, both origins kept
firewall-v2.log:301   network_deny 203.0.113.92 -> ...
firewall-v3.log:067   network_deny 203.0.113.92 -> ...  (duplicate)
# canonical event keeps provenance: origins=[firewall-v2.log:301, firewall-v3.log:067]
# counted once as accepted, once as duplicate, so reconciliation still balances

The reconciliation identity, and determinism

Your reconciliation.json had to satisfy, for every source, one simple equation: 
accepted  +  quarantined  +  duplicates  ==  manifest row count
If that does not hold, a row was lost or double-counted somewhere, and the timeline cannot be trusted. Determinism is the twin of this: run the clean build twice and the normalized-timeline hash and the results hash must be identical. If they drift between runs, something in your pipeline is non-deterministic (usually unstable sort order or a map iterated without sorting), and a reviewer cannot reproduce you.

1.4The four required machine outputs (plus timeline and graph)

A contract-complete clean build produced four machine outputs, plus the normalized timeline and the campaign graph, plus the human artifacts. If any of these were missing or empty, the pipeline marks simply could not be earned, because there was nothing to inspect.

OutputWhat it contains
clean.dbThe normalized store: every accepted canonical event across all five sources and all three schema versions, each carrying its source file, row locator, corrected UTC time, and resolved identity. This is the single source of truth every later query runs against.
results.jsonThe structured findings: the three reconstructed campaigns and the 96 review verdicts, in machine-readable form, each tied to evidence locators.
quarantine.csvEvery rejected row with its reason (invalid_json, missing_time, unsupported variant) and its source file and row locator. This is your honesty record: nothing dropped without a name.
reconciliation.jsonPer-source counts proving accepted + quarantined + duplicates == manifest, so a reviewer can confirm no data was lost or invented.

The normalized timeline is the ordered, UTC, deterministic sequence of all accepted events, with stable tiebreaks for equal timestamps. It is what you query for each campaign pivot. The campaign graph (or an equivalent structured campaign result) expresses each campaign as nodes (actors, hosts, IPs, objects) and ordered edges, where each edge points to the two independent raw locators that prove it. Alongside these, a complete submission also delivered all 96 verdicts, a test result and repeatability evidence, and a README, manifest, integrity attestation, and continuity record. Equivalent filenames were fine as long as the schema and purpose were unambiguous.

1.5The three campaigns, in full

This is where the most marks lived and where the clearest advice applies: a campaign is a story with an ordered chain of evidence, not a list of matching keywords. For every campaign you needed ordered UTC events; actor, host, IP, and object reconciled to canonical values; two independent raw locators for every claimed edge; one rejected alternative; a confidence level; and one concrete next collection action. An edge proven from a single source, or a campaign asserted from one keyword hit, did not count.

Campaign 1 · slow spray and compromise

The story. An attacker at 198.51.100.124 ran a low-and-slow password spray against the amina-ad4 host and the amina identity: many failed logins spread out over time to stay under alerting thresholds, then eventually one success, then a follow-on action using that access.

The exact pivots. Source IP 198.51.100.124; target identity amina (remember the alias resolution) on host amina-ad4; a spray or low-and-slow failure pattern; then a successful authentication; then a consequence of that access.

The ordered chain that proves it. 
# all times UTC, from the normalized timeline
1. many auth fail events, actor=amina, host=amina-ad4,
   src=198.51.100.124, spread over time    [auth source]
2. one auth success, same actor/host/src           [auth source]
3. follow-on activity from that access
   (session / endpoint / network action)   [second source]
The mark was for proving the sequence ending in success and follow-on, not for counting failures. Repeated failures alone are a spray attempt; they are not a compromise.

One edge proven from two independent sources (worked). Take the compromise edge, the claim "the spray succeeded and was used." Prove it from two sources that do not depend on each other: the auth source shows the failure-then-success transition on amina from 198.51.100.124, and a second, independent source (for example a firewall network_deny or endpoint event from that same host and IP in the minutes after the success) shows activity consistent with the access being used. Two independent feeds agreeing on the same actor, host, IP, and time window is what turns a guess into evidence.

Rejected alternative: a legitimate user fat-fingering their password repeatedly then logging in. Rejected because the failures come from a single external IP at a machine-like cadence and are followed by activity that does not match the user's normal pattern. Confidence: high, given two independent sources on the compromise edge. Next collection action: pull full session and process telemetry from amina-ad4 for the window after the success to scope what the access touched.

Campaign 2 · web to endpoint exfiltration

The story. Activity pivoting through the web tier at 203.0.113.92 and 203.0.113.147, tied to a specific request req-v1-x1, ending in a large data transfer of 884,944 bytes leaving the environment, correlated from web activity through to the endpoint.

The exact pivots. IPs 203.0.113.92 and 203.0.113.147; request id req-v1-x1; the 884,944 byte transfer; and a link from web activity to the endpoint and to data leaving.

The ordered chain that proves it. 
# all times UTC, endpoint events already clock-corrected (-3900s)
1. web_request from 203.0.113.92 / 203.0.113.147,
   request req-v1-x1                         [web source]
2. endpoint activity on the tied host,
   correlated by actor/host/time             [endpoint source]
3. transfer of 884944 bytes off the host     [web / network source]
One edge proven from two independent sources (worked). Take the exfiltration edge, "884,944 bytes left the host." The web source shows request req-v1-x1 from 203.0.113.92 with the 884,944 byte payload; the endpoint source shows the matching file or process activity on the tied host at the corrected time. This is precisely where the clock fix earns its keep: without minus 3,900 seconds the endpoint step lands an hour off and the two sources no longer line up.

Rejected alternative: a routine large download or backup. Rejected because the byte count matches a specific tracked request id and the endpoint activity is not an approved backup job on the change record. Confidence: high on the transfer size and request id (they are exact), medium on intent. Next collection action: retrieve the full web payload and proxy logs for req-v1-x1 and the destination reputation for both IPs. A generic endpoint-to-DNS query is not automatically this campaign; the byte count, request id, and web-to-endpoint join are what make it Campaign 2.

Campaign 3 · insider removable-media copy

The story. An insider, nora.contractor, used a removable device usb-v1 to copy a sensitive file, synthetic-payroll-q2.csv, off an endpoint. This is a people-and-process incident as much as a technical one.

The exact pivots. Actor nora.contractor; device usb-v1; object synthetic-payroll-q2.csv; endpoint or file activity; and a removable-media context.

The ordered chain that proves it. 
# all times UTC, endpoint events clock-corrected
1. removable device usb-v1 attached,
   actor=nora.contractor                     [endpoint source]
2. file synthetic-payroll-q2.csv accessed
   / copied to usb-v1                         [endpoint / file source]
3. corroborating event tying actor+device
   +object together                          [second source]
One edge proven from two independent sources (worked). Take the copy edge, "nora.contractor copied synthetic-payroll-q2.csv to usb-v1." The endpoint source shows the file access or copy to device usb-v1; a second, independent record (a device-attach event or file-audit entry) confirms the same actor, device, and object in the same window. Two independent records on the same three pivots is the proof.

Rejected alternative: an approved data export or a sanctioned transfer to portable media. Rejected because no change record or approval covers this actor moving this file to this device, and the file is sensitive payroll data. Confidence: high on actor, device, and object (all exact pivots), medium on intent pending an HR and manager check. Next collection action: preserve the endpoint disk image and the USB device metadata, and open an insider-risk case with HR rather than acting unilaterally.

Where people went wrong on campaigns

Claiming a campaign from keyword matches alone; passing off a generic endpoint-to-DNS query as the exfiltration; showing many failed logins but never proving the later success and follow-on; proving edges from a single source instead of two independent ones; skipping the clock fix so the endpoint steps never lined up; and piling up huge locator counts around a conclusion that was simply wrong. A wrong conclusion with a hundred citations still scores as a wrong conclusion.

1.6The 96 review candidates

Every intern was assigned 96 review candidates, each a flagged activity with a unique REVIEW-#### id. The correct aggregate was 80 benign and 16 escalated. But the aggregate was never the point: you had to inspect all 96 unique ids and record a structured verdict for each, tied to a locator. Writing "80 and 16" in prose without the itemised rows earned almost nothing on the evidence and false-positive criteria, because there was no proof you had actually looked.

A row is benign only if all eight of these checks reconcile. If even one fails, the row escalates.

#CheckWhat it confirms
1Activity id presentThe row points to a real, identifiable activity, not a vague description.
2Asset matchThe asset in the activity is the asset the change or approval was for.
3Actor or owner matchThe actor performing it is the authorised actor or owner, not a lookalike.
4Correct approverThe person who approved it was actually entitled to approve it.
5APPROVED statusThe structured status field says approved, not pending or denied.
6In-window timestampIt happened inside the authorised change or maintenance window.
7Covering change recordA specific change record exists that covers this activity.
8Evidence locatorYou can point to the exact source and row that shows all of the above.

Worked example: a benign row passing all eight (illustrative)

REVIEW-0007  approved vulnerability scan
  1 activity id     ACT-scan-8841                present
  2 asset           subnet 203.0.113.0/24        matches change CR-2211
  3 actor           svc-scanner                  = authorised scanner identity
  4 approver        approved by security lead     entitled to approve
  5 status          APPROVED                      structured field
  6 timestamp       2026-07-13T02:00:00Z          inside 01:00-03:00 window
  7 change record   CR-2211 covers this scan      covering record exists
  8 evidence        firewall-v2.log:412, cr-2211  locator provided
  => VERDICT: benign (approved scanner family)
All eight reconcile, so this is correctly benign, and the verdict cites its evidence.

Worked example: an escalated row failing exactly one check (illustrative)

REVIEW-0063  backup job to external target
  1 activity id     ACT-backup-5502              present
  2 asset           payroll share                matches change CR-3040
  3 actor           svc-backup                   = authorised backup account
  4 approver        approved by ops lead         entitled
  5 status          APPROVED                     structured field
  6 timestamp       2026-07-13T14:20:00Z         FAILS: window was 22:00-23:00
  7 change record   CR-3040 covers backups        exists
  8 evidence        endpoint clock-corrected row  locator provided
  => VERDICT: escalate. Failed check 6 (out-of-window timestamp).
Seven checks pass, but the activity ran hours outside its authorised window, so it escalates, and the verdict names which check failed (check 6). Naming the failed check is what turns an escalation into a usable finding.

The benign families you should recognise: approved scanner activity (including the supplied scanner context), approved backup activity tied to the svc-backup service account, and signed updater activity. Seeing one of these families is a strong hint toward benign, but you still had to run all eight checks. A family match is a starting point, not a verdict.

The trap that cost the most false-positive-restraint marks

Do not mark an escalated row benign just because its own narrative discusses a benign hypothesis and then rejects it. Some rows are written to sound reassuring while the structured facts say otherwise. Judge on the structured status and the eight checks, not on the prose. Equally, do not escalate a genuinely benign, approved, in-window, change-covered activity just to look thorough. Both mistakes are false-positive-restraint failures.

1.8The scoring caps, and the reasoning behind each

Some submissions hit a published technical cap that held the final score below the raw sum of the criteria. A cap is not an automatic elimination; it is a ceiling that reflects a method too weak to trust at full marks.

CapCeilingWhy
Grep-only analysis55Searching for strings finds keywords, not chains. It cannot prove an ordered sequence across two independent sources, which is the core of the task, so it is capped below a pass-with-confidence.
Single-line campaign attribution60Naming a campaign in one line asserts a conclusion without walking the evidence. The work of proving pivots, order, and two sources per edge simply was not shown.
Screenshots without raw rows or queries50A screenshot shows a result but not the reproducible path to it. A reviewer cannot rerun a picture, so it cannot earn full evidence or reproducibility credit.
Copied input earns nothingno authored creditReproducing the supplied pack, an assignment PDF, or provided context is not your analysis. Authored-work credit attaches only to what you produced.
Huge locator counts do not fix a wrong conclusionno rescueVolume of citations cannot repair an incorrect finding. A hundred locators pointing at the wrong campaign is still the wrong campaign; correctness is judged first.

Undeclared source edits or fabricated evidence went to integrity review rather than a numeric cap. The honest path always scored better than the impressive-looking shortcut, because the whole rubric is built to reward proof a second analyst can reproduce.

1.9Your checklist for a top SOC answer

  • A normalizer that runs, handling all five sources across all three schema versions each through explicit adapters.
  • Every accepted event carries its source file and row locator (provenance is not optional).
  • Malformed rows quarantined as invalid_json, timeless rows as missing_time, unknown variants flagged, none silently dropped.
  • The endpoint clock corrected by minus 3,900 seconds (09:05:00 becomes 08:00:00).
  • Identity aliases resolved: amina@example.invalid and EXAMPLE\amina both become amina.
  • Duplicates removed with provenance kept, and stable ordering for equal timestamps.
  • Reconciliation holds for every source: accepted + quarantined + duplicates == manifest.
  • Two clean runs produce identical normalized and result hashes.
  • All four machine outputs delivered and non-empty, plus the normalized timeline and campaign graph.
  • All three campaigns as ordered UTC chains, each edge proven from two independent raw sources.
  • Each campaign carries a rejected alternative, a confidence level, and one next collection action.
  • All 96 REVIEW-#### ids adjudicated individually, not summarised as "80 and 16."
  • Every benign verdict passes all eight checks; every escalation names the check it failed.
  • No over-escalation of approved, in-window, change-covered activity, and no benign verdict trusting a reassuring narrative over the structured status.
  • A README, manifest, and integrity attestation that let another analyst rerun your build to the same result.
Track 2 · Ethical Hacking

Ethical Hacking: disciplined recon to a proven foothold

This track asked you to think and behave like a professional penetration tester working under a signed engagement letter. That framing matters more than any single technical step, so read this before anything else. A professional is not the person who finds the most services or fires the most packets. A professional is the person who stays inside the authorised boundary, keeps a defensible record of every action, turns noisy tool output into clean structured evidence, and can prove a foothold with a chain that another engineer can follow and reproduce. Every part of the rubric below is really a test of that discipline.

Concretely, you built a reconnaissance engine that had to do four things at once: stay strictly inside an authorised scope, stay under a hard request budget, convert several different tool output formats into one clean normalized record shape, and finally reach a foothold by retrieving your own user.txt value together with the full request chain that produced it. The engine had a fixed command-line interface and a fixed output layout so a reviewer could run it the same way for everyone. The lab itself was personalised: each intern's lab was derived from a private marker, so there was never one shared answer key of ports and flags. That is deliberate. It means you could not pass by copying a friend, and it means the only proof that counts is proof generated by your own run against your own lab.

As you read, keep one sentence in mind. Your score measured what your delivered files actually proved, not how much you wrote, how many services you listed, or how polished the report looked. The interns who ran their engine, kept the outputs, and reconciled them scored well. The interns who described a great engine but delivered an empty raw/ folder, or who pasted a flag value with no request behind it, did not, however good the prose.

The track was marked out of 100 across five criteria. The table gives the headline; the paragraphs after it explain what each criterion was really testing, because the difference between a middling and a strong score almost always lived in that detail.

Discovery completeness20Normalized records carrying all nine required fields, plus the extra virtual-host fields, across the services your run actually observed.
Foothold proof20Your own user.txt value retrieved through the full request chain and reconciled across every piece of evidence.
Evidence and reporting15A clear report, evidence index, scope register, and request ledger that all agree with each other and with the raw output.

Scope and safety, 20 marks. This criterion answered one question: could you be trusted with a live target? It rewarded an engine that made every authorisation decision before it opened a socket, that never sent a single packet to the out-of-scope trap, and whose delivered ledger stayed under the ceiling. It is the criterion where good intentions in the source code counted for nothing if the behaviour on disk contradicted them. A comment saying "we respect scope" next to a ledger showing a request to the trap endpoint lost these marks in full.

Engine design and tests, 25 marks. This was the largest single criterion because it measured whether you built an engine at all, as opposed to a shell script that shells out to a scanner and pipes the result to a file. It rewarded a parser-and-adapter design: one tested adapter per input format, each with tests that feed it a known input and assert on the exact normalized output. Tests that never call your code, or that assert True, earned nothing here regardless of how many there were.

Discovery completeness, 20 marks. This measured whether your discovery turned into clean, complete, structured data. Every normalized service record needed all nine required fields, populated and correct, and virtual-host records needed the additional fields. Completeness here is about the records being whole and faithful to what your run observed, not about padding the list with services you never actually saw.

Foothold proof, 20 marks. This measured whether you reached a foothold and could prove it. The proof was your own authenticated user.txt value plus the chain behind it. A flag-shaped string with no chain was not proof; the chain with no value was incomplete; the two together, reconciled across your evidence, earned the marks.

Evidence and reporting, 15 marks. This measured whether a reviewer could believe you. It rewarded a report, an evidence index, a scope register, and a request ledger that told one consistent story and that matched the raw files on disk. Contradictions between artifacts (a report claiming a service the normalized data never lists, a ledger that disagrees with the raw responses) cost marks here even when the underlying work was real.

2.2Scope and safety in depth

Because scope discipline gated so much, it is worth being precise about exactly what was authorised and exactly what the engine had to check. The generated scope.csv listed loopback endpoints, each marked IN or OUT. Only the endpoints marked IN were authorised. The OUT endpoint was not a mistake and not an afterthought; it was a deliberate scope test placed in your file to see whether your engine would touch it. It had to receive zero requests. Not one connection attempt, not one probe, not one "just checking if it is alive" packet. In a real engagement, the equivalent endpoint might be a neighbouring company's server on the same subnet, and touching it is a crime. The lab treats it with the same seriousness.

The order of operations is the whole point. Before the engine opened a socket or sent a single byte, it had to evaluate every one of these checks and let the target through only if all of them passed:

  • Host or resolved IP. Resolve the name if you were given a name, then check the address you will actually connect to. Checking the hostname string alone is not enough, because a name can resolve to an address outside scope.
  • CIDR. The resolved address must fall inside an authorised range. This is the check that stops you wandering onto a neighbouring host.
  • Protocol. Only the authorised protocol for that endpoint. A UDP probe to a TCP-only authorisation is out of scope.
  • Port. The port must be inside the allowed range for that endpoint. A port one above the allowed ceiling is out of scope, however tempting.
  • Rate. The engine must honour the requested rate so it never floods the target.
  • Total request budget. The running total of requests must stay under the mission ceiling.

The mission ceiling was 240 requests. This is a total across the whole run, not a per-port or per-tool figure. A budget object sitting in your source code that says "max 240" did not earn full safety credit if the delivered target ledger showed more than 240 requests actually went out. The ledger is the truth; the intention in the code is not.

Worked example: allowed versus denied (fictional values)

Suppose your generated scope authorised a single endpoint: host 127.0.0.1 resolving inside 192.0.2.0/28, protocol TCP, ports 8000 to 9000, and it also listed a trap endpoint marked OUT at the decoy hostname staging.decoy.invalid. Here is how the pre-flight check should decide, before any socket opens:

Candidate requestFailing checkDecision
TCP to 192.0.2.14 port 8443noneALLOW, then connect
TCP to 192.0.2.16 port 8443CIDR (outside the /28)DENY, no socket
TCP to staging.decoy.invalid port 8443host (the OUT decoy)DENY, no socket
TCP to 192.0.2.14 port 9443port (above 9000)DENY, no socket
UDP to 192.0.2.14 port 8443protocol (TCP only)DENY, no socket
request number 241 to a valid endpointbudget (ceiling 240)DENY, no socket

Note that only the first row ever reaches the network. Every DENY is recorded (a denied attempt is useful evidence that your guard works) but no packet leaves. The /28 gives sixteen addresses, so 192.0.2.14 is inside it while 192.0.2.16 is the first address of the next block and is correctly rejected.

The single most common failure: a guard that was never wired in

By far the most frequent way interns lost scope marks was writing a perfectly correct scope guard and then never calling it on the path that actually opens the socket. The function existed, it had tests, it returned the right answer when asked. But the code that connected to a target called the socket directly, or went through a helper that skipped the guard. The result: a beautiful is_in_scope() function and a ledger showing traffic to the trap. The lesson is that the guard must sit on the one and only path to the network, so there is no way to open a connection without passing through it. If there are two ways to reach a socket in your engine, one of them will eventually be the unguarded one. Reviewers checked the delivered ledger against the scope, so an unwired guard was visible immediately.

2.3The required interface and output

The engine had a fixed interface so a reviewer could run everyone's the same way. It was invoked like this:

recon-engine --target 127.0.0.1 --scope lab-runtime/scope.csv --output run/ --rate 25

And it had to produce this output layout under the directory given by --output:

run/
  run.json          # run metadata: target, scope, timing, request ledger, totals
  raw/<tool>/        # untouched output from each tool, one subdirectory per tool
  normalized/assets.jsonl   # one normalized record per line
  report.html       # the human-readable report
  errors.jsonl      # one record per malformed or rejected input

Each part carries weight. The run.json is the run's spine: it records what you targeted, which scope you loaded, when things happened, and the request ledger that proves you stayed under budget. The raw/<tool>/ tree is your chain of custody: the untouched output of each tool, preserved exactly as produced, so every normalized record can be traced back to the bytes it came from. An empty raw/ is not evidence of anything, and it undermines every record that claims to derive from it. The normalized/assets.jsonl file is your structured findings, one JSON object per line. The report.html is the story a human reads. The errors.jsonl is where malformed inputs and rejected records go, so nothing is silently dropped.

The nine required normalized fields

Every normalized service record needed all nine of these fields, populated and correct:

FieldMeaning
observed_atWhen this observation was made, in UTC.
targetThe host or address the observation is about.
portThe port. A record with no port is invalid.
protocolTCP or UDP.
serviceThe service identified on that port, for example https or ssh.
source_toolThe tool that produced the observation.
source_fileThe exact raw file the record was parsed from, so it traces to raw/.
confidenceHow confident the identification is.
notesFree text for anything a reviewer needs to interpret the record.

Virtual-host records needed five more fields on top of the nine, because a virtual host is judged by how its response differs from a baseline: status (the HTTP status code), length (the response body length), title (the page title), redirect (any redirect target), and the baseline-difference fields that record how this response differed from the wildcard baseline. Those difference fields are what let you decide whether a virtual host is real or just the default catch-all answering under a different name.

One fully-populated normalized record (fictional)

{
  "observed_at": "2026-07-20T14:02:11Z",
  "target": "192.0.2.10",
  "port": 8443,
  "protocol": "tcp",
  "service": "https",
  "source_tool": "portscan",
  "source_file": "raw/portscan/scan-01.xml",
  "confidence": "high",
  "notes": "TLS service, self-signed certificate, banner suppressed"
}

Notice that source_file points straight into raw/. That is what makes the record verifiable: a reviewer can open that exact file and confirm the record is faithful to it. A record whose source_file points at nothing, or whose values do not match the raw bytes, is not trustworthy evidence.

2.4Parser and behaviour answers in full

The engine was tested against several sample input formats and several edge-case behaviours. Below are the canonical answers. Treat them as the acceptance tests your parsers had to pass. The values are the published public fixtures, so they are safe to teach here; your own lab used its own personalised values, but the parsing rules are identical.

The four parse cases

CaseInputCanonical parsed result
PARSE-01XML scan resulthost 192.0.2.10, port 8443, protocol TCP, service https, state open
PARSE-02JSON scan resultpreserve both target.invalid and 192.0.2.11, port 2222, protocol TCP
PARSE-03HTTP response linehost ops.target.invalid, port 8443, status 401
PARSE-04line-protocol recordhost 192.0.2.12, port 8022, protocol TCP, service ssh, version OpenSSH_9.2

Two general rules sit underneath these. First, malformed input goes to errors.jsonl; it is never silently dropped and never guessed at. Second, a record without a port is invalid, because a service observation with no port cannot be acted on or reconciled. In PARSE-02 the point is that both the hostname form (target.invalid) and the address form (192.0.2.11) are preserved, because throwing one away loses information a later step may need.

Scope behaviour at the boundary

The scope logic had to give exactly these answers on the public fixture:

  • Permit 192.0.2.14, which lies inside the supplied /28.
  • Reject 192.0.2.16, which lies just outside that /28.
  • Reject the decoy hostname (the OUT trap), whatever it resolves to.
  • Reject port 9443 when the allowed range ends at 9000.

Virtual-host, resume, dedup, and fallback behaviour

  • Virtual hosts. A virtual host whose response is identical to the wildcard baseline is suppressed, because it is just the default answering. A virtual host with a material difference from the baseline is retained, because that difference is a real finding.
  • Resume. An interrupted run, when resumed, returns the next unfinished port and carries on from there. A run whose checkpoint is already complete returns no next port, because there is nothing left to do.
  • Deduplication. Two identical TCP service observations deduplicate to a single row, because they describe the same fact. An equivalent-looking TCP observation and UDP observation stay as two rows, because protocol is part of a service's identity and they are genuinely different services.
  • Fallback. A missing optional tool triggers the documented fallback and the run continues. A missing required parser with no fallback causes the engine to exit non-zero, because it cannot honestly complete.

Why one tested adapter per format, and why a single shell wrapper fails

The engine design criterion specifically rewarded a parser-and-adapter architecture: one small, tested adapter per input format, each taking raw bytes and returning normalized records, each with tests that feed a known input and assert on the exact output. This is not bureaucracy. It is what lets you prove each format is handled correctly in isolation, and it is what lets a reviewer see, format by format, that your engine does what you claim.

A single monolithic shell-command wrapper (one script that runs a scanner and greps its stdout) fails this for concrete reasons. It cannot be unit-tested against a fixture without running the external tool, so it cannot prove its parsing in isolation. It usually handles only the one output shape it happened to see, so a format variation slips through as garbage. And it tends to blur the raw-versus-normalized boundary, so provenance is lost. A wrapper can produce output; it cannot demonstrate correctness. That is why it does not earn the design marks even when it appears to work.

A small worked parse (fictional)

Suppose the adapter for line-protocol input receives this single raw line from raw/svc-probe/probe-02.txt:

192.0.2.12:8022/tcp open ssh OpenSSH_9.2

The correct adapter emits exactly one normalized record and writes nothing to errors.jsonl:

{
  "observed_at": "2026-07-20T14:05:40Z",
  "target": "192.0.2.12",
  "port": 8022,
  "protocol": "tcp",
  "service": "ssh",
  "source_tool": "svc-probe",
  "source_file": "raw/svc-probe/probe-02.txt",
  "confidence": "high",
  "notes": "banner OpenSSH_9.2"
}

If the same file also contained a line with no port, that second line would produce no normalized record and one entry in errors.jsonl explaining why it was rejected. The good line and the bad line are both accounted for; neither is invented and neither is silently lost.

2.5The foothold in full

The foothold is where interns most often confused activity with proof, so read this slowly. There was no universal user flag. Each lab start derived its own profile, ports, route, credentials, virtual-host behaviour, and user.txt value from the intern's private marker. That means the only correct answer for you was the value your own authenticated request returned from your own lab. There was never a shared flag to look up, and there was never a way to guess it.

What actually counted as proof

The correct foothold proof was the value returned from your own authenticated user.txt request, reconciled across all of the following so they tell one consistent story:

  • the raw response that contained the value;
  • the target request ledger showing the request that fetched it;
  • the normalized record for the service you reached;
  • the route proof showing how you got there;
  • the credential evidence showing where the credentials came from;
  • the report narrating the chain;
  • the evidence index pointing at each artifact;
  • the hashes that let a reviewer confirm nothing was altered.

The chain that produced that value ran in three linked steps, and each step had to be evidenced, not asserted:

  1. Route to the virtual host. Your discovery found a virtual host that differed materially from the wildcard baseline. That difference was the doorway, and your baseline-difference fields are the evidence that it was real rather than the default catch-all.
  2. Recover the credentials. Following that route led you to credentials. The credential evidence has to show where they came from, not simply that you had them.
  3. Make the authenticated request. With the credentials you made an authenticated request that returned user.txt. That request appears in the ledger and its response appears in raw/.

Where people went wrong on the foothold

  • Treating the room marker as the flag. The room marker is not the flag. Presenting it as the answer showed the chain was never actually walked.
  • A flag string with no chain. A flag-shaped value sitting in a text file, with no request and response behind it, is not full proof. Anyone can type a string. Proof is the request that produced it.
  • Reading or editing the lab file. Opening local_lab.py to read the value out of it, or editing it, earned no discovery credit at all. That is not finding the flag; it is looking at the answer sheet, and the reviewers could see it in the evidence.
  • The value without reconciliation. Even a genuine value lost marks if the ledger, normalized record, route, credentials, report, index, and hashes did not line up. A foothold you cannot reconcile is a foothold a reviewer cannot trust.

One firm rule for your own write-up: do not invent or guess a value. If your run did not reach user.txt, say so honestly and show how far the chain got. An honest partial chain is assessable and can earn real credit for the steps you did prove; a fabricated flag is an integrity problem and earns nothing.

2.7The scoring caps, and why each exists

Some outcomes triggered a cap or a review that no amount of narrative could undo. Each one exists to stop a specific way of appearing to succeed without actually succeeding.

  • No runnable implementation is subject to the published technical cap. If there was no engine that actually ran, the technical score was capped, because a description of an engine is not an engine.
  • Hard-coded runtime flags trigger an integrity review. If the user.txt value or route was baked into the source rather than discovered at runtime, it went to integrity review and a cap applied, because that is presenting the answer as if it were found.
  • A ledger above 240 requests loses points. Exceeding the mission ceiling cost meaningful safety and validation marks, because staying under budget is a core safety property, not a nice-to-have.
  • An empty raw/ directory is not evidence. Without preserved raw output there is no chain of custody, so normalized records that claim to derive from it cannot be trusted and the discovery marks fall away.
  • Vacuous tests earn nothing. Tests that never invoke the engine, or that assert trivially true statements, prove nothing about the code and so earned no engine-and-tests credit no matter how many there were.

2.8Your checklist for a strong Ethical Hacking submission

  • Only the IN loopback endpoints are treated as authorised; the OUT trap receives zero requests.
  • The scope guard sits on the one and only path to a socket, checking host or resolved IP, CIDR, protocol, port, rate, and budget before any connection.
  • The delivered request ledger stays at or under 240 requests.
  • The engine runs through its published interface and produces run.json, a populated raw/<tool>/, normalized/assets.jsonl, report.html, and errors.jsonl.
  • Every normalized record carries all nine required fields; virtual-host records add status, length, title, redirect, and baseline-difference.
  • Each input format has its own tested adapter, and the tests actually invoke the engine.
  • Malformed input lands in errors.jsonl; a record with no port is treated as invalid.
  • Resume continues at the next unfinished port; identical TCP observations dedupe while equivalent TCP and UDP stay separate; a missing optional tool falls back and a missing required parser exits non-zero.
  • The foothold is your own user.txt value, reached through route, credentials, and an authenticated request, and reconciled across raw response, ledger, normalized record, route proof, credential evidence, report, evidence index, and hashes.
  • No value is invented; an honest partial chain is shown where the run stopped short.
Track 3 · Governance, Risk and Compliance

GRC: real gaps, honest evidence, controls that run

This track asked you to think like a compliance engineer, not a report writer. You received a fictional company's security posture pack: a set of policies, screenshots, tickets, exports, and an assigned control-state input. Your job was to find the real gaps in that posture, map each gap to the control family that must fix it, judge every piece of evidence honestly, implement exactly three machine-enforceable controls in code (Open Policy Agent, written in Rego), and draft a policy addendum that could actually be enforced. The single hardest lesson of the whole track is this: a beautiful document earned very little on its own. What earned marks was work that ran against your own assigned state and produced a defensible decision for every asset. Read this section once to see the shape of a strong answer, then read it again next to your own submission and your reviewer notes so you can see exactly where the two part ways.

3.1How it was scored

The rubric had five criteria that sum to 100. Nothing was awarded for effort, length, or polish by itself. Each criterion rewarded a specific, checkable behaviour in your delivered files.

CriterionMaxWhat earned the marks
Gap accuracy25A typed gap register that correctly classified the seven planted issues, including the two that were traps and were NOT simple gaps.
Control mapping20Each real gap mapped to the correct control family and to a requirement the control must enforce, including fixing the one planted bad mapping.
Evidence judgment20A recorded verdict for every artifact that separated observed fact from interpretation, and refused to over-claim from weak proof.
Exactly-three-control decision20Exactly three data-driven Rego controls that evaluate your assigned state, default to deny, and emit a complete decision per asset.
Enforceable drafting15Policy clauses that name an owner, scope, requirement, exception route, enforcement evidence, and review cadence.

Gap accuracy (25). This measured whether you found the genuine problems and, just as important, whether you resisted calling two deliberate distractors "gaps" when they were not. A register that flagged all seven items as failures scored worse than one that flagged five and correctly reasoned that two were either risk-based judgement calls or contextual. Full marks required a typed register: each entry naming the issue, the class of gap (policy, process, privacy, evidence, or implementation), the affected assets or population, and the verdict with its reasoning. Prose paragraphs that buried the finding lost marks because a reviewer could not reconcile them to a control.

Control mapping (20). Finding a gap is only half the work. Each real gap had to point at the control family responsible for closing it and, crucially, at what that control must require. "This maps to access control" is not a mapping; "this maps to the privileged-identity control, which must require phishing-resistant MFA on every privileged identity and produce an enforcement record" is. One item in the pack came pre-mapped incorrectly on purpose, and correcting that mapping was worth real marks.

Evidence judgment (20). Compliance lives or dies on the honesty of its evidence. This criterion rewarded a verdict for every artifact that split what you literally observed from what you inferred, and that assigned a confidence level. The people who scored well said "this screenshot proves X about a subset at a past date" rather than "this proves the estate is encrypted." Over-claiming from a weak artifact cost more than admitting the artifact was insufficient.

Exactly-three-control decision (20). This was the executable heart of the track. Three controls, no more and no fewer, each one a data-driven Rego package that reads your assigned input, defaults to deny, and emits a full decision for every asset. Marks here depended almost entirely on whether the code ran and whether it evaluated state rather than hard-coding answers. A polished write-up with no running controls could not pass the technical assessment for this project.

Enforceable drafting (15). The addendum had to be enforceable, not aspirational. Every clause needed an owner who is accountable, a scope that says who and what it covers, a concrete requirement, a route to request an exception, the evidence that proves enforcement, and a review cadence. A clause that said "all devices should be secure" earned nothing because no one could be held to it and nothing could check it.

3.2The seven planted gaps, in full

The pack contained seven items placed deliberately. Five were genuine gaps. Two were traps: one was a judgement that is only a gap if you overstate it, and one was a document whose age is context, not a defect. Getting the two traps right separated strong candidates from candidates who simply flagged everything.

Gap 1 · Optional privileged MFA (policy and implementation gap)

The pack showed a screenshot in which several administrators had multi-factor authentication enabled, and a policy that recommended MFA for privileged accounts. This is a genuine gap on two levels at once. It is a policy gap because "recommended" is not "required"; an optional control is an unowned control. It is an implementation gap because a screenshot showing that some admins use MFA does not prove that every privileged identity is covered, nor that the factor is phishing-resistant.

What a strong write-up contained: the finding that the control must be mandatory, not optional; a requirement for phishing-resistant MFA (not SMS or one-time codes that can be relayed) on every privileged identity, including break-glass and service-linked admin accounts; and the explicit statement that a screenshot is not evidence of a rule. A rule is proven by policy text plus an enforcement mechanism that denies privileged access without the required factor, not by a picture of a few accounts. The correct verdict is "policy and implementation gap; requires a mandatory phishing-resistant MFA rule for all privileged identities, enforced and evidenced."

Gap 2 · Manager-requested access reviews (policy, process, and evidence gap)

The pack described access reviews that happen "when a manager asks for one." That is not an access-review programme; it is an occasional favour. This is a three-part gap: policy (no defined obligation), process (no defined mechanism), and evidence (nothing retained to prove a review ever occurred).

What a strong write-up contained: a defensible control that defines a cadence (for example quarterly for privileged access, at least annually for standard access), a named owner accountable for the programme, an explicit scope (which systems and which identity classes), reviewer independence where segregation of duties requires it (the person reviewing should not be the person who granted or benefits from the access), retained evidence of each review and its decisions, an overdue escalation path when a review is missed, and a remediation step that actually removes access found to be inappropriate. A review that finds problems but never revokes anything is theatre. The correct verdict names all of cadence, owner, scope, independence, evidence, escalation, and remediation.

Gap 3 · Over-broad BYOD inspection (policy, privacy, and process gap, with a planted bad mapping)

This is the item most people got half-right. The pack proposed inspecting personal (bring-your-own) devices broadly, and it came pre-mapped to a single data-loss-prevention control as if that control alone justified the inspection. That mapping is the planted trap. Treating a technical data-loss control as sufficient authority to inspect personal devices ignores the entire privacy dimension of the problem.

What a strong write-up contained: first, the correction of the mapping. The data-loss control is relevant but is not the controlling consideration; the gap is fundamentally a privacy and personal-data problem. A defensible correction discusses privacy and protection of personal data on the device, acceptable-use boundaries, notice to the device owner about what is inspected, a lawful basis for any inspection, data minimisation (inspect only what is necessary, ideally only the managed work container rather than the whole device), retention limits on anything collected, proportionality (the inspection must be no broader than the risk warrants), and a legal review before any such programme goes live. The correct verdict is "over-broad; inspection of personal devices must be minimised, proportionate, noticed, lawfully based, and legally reviewed; the single data-loss control mapping is insufficient." Do not quote licensed control-standard text to make this point; describe the requirement in your own words.

Gap 4 · Helpdesk-only incident route (policy and process gap)

The pack routed all incidents through the general helpdesk with no security path. A security incident that sits in a helpdesk queue behind password resets is an incident that is not being handled.

What a strong write-up contained: a control that adds security triage so suspected security events are recognised and pulled out of the general queue quickly; clear incident ownership so a named function owns the response rather than a ticket bouncing between teams; a regulatory and privacy escalation path so events that may involve personal data or reportable breaches reach the people who must notify regulators or affected individuals within the required time; defined response times keyed to severity; and retained evidence of the response for later review and for any regulator. The correct verdict is "policy and process gap; needs a dedicated security incident path with triage, ownership, regulatory and privacy escalation, response-time targets, and retained evidence."

Gap 5 · Forced 90-day rotation (a trap: too-absolute conclusion, not a simple gap)

The pack asserted that forcing every user to change their password every 90 days makes the organisation safer. The trap here is to nod along, or to flag it as a missing control. Neither is right. The claim that frequent forced rotation is automatically safer is too absolute. Blanket short rotation drives users toward predictable, incremented passwords and adds little against modern credential theft.

What a strong write-up contained: the correct framing that credential management should be risk-based. Rotate on evidence of compromise; apply stronger, targeted controls to privileged and service accounts (which is where rotation and secret hygiene genuinely matter); prefer length, uniqueness, and phishing-resistant factors over calendar-driven churn for ordinary users. The correct verdict is not "gap" and not "fine as written"; it is "the stated conclusion is too absolute and should be replaced with a risk-based credential policy." Marking this a plain gap, or accepting the 90-day claim uncritically, both lost marks.

Gap 6 · Stale MDM screenshot (weak evidence, not proof of compliance)

The pack included a mobile-device-management screenshot dated well in the past. It showed 91 managed devices and 89 of them encrypted. The current device population, however, is 176 devices plus an unknown number of personal devices, and the screenshot carried no export metadata (no verifiable date, query, or scope of the export).

What a strong write-up contained: the honest reading. This is limited historical evidence for a subset of a now-larger estate. It does not prove current, universal encryption. Ninety-one of a then-population is not 176 of the current population, an old date is not today, 89 encrypted is not 100 percent even within that subset, and with no export metadata you cannot even fully trust the snapshot's scope. The correct verdict rejects the screenshot as proof of current compliance and states what would actually prove it: a current, dated, scoped export covering the full managed population, ideally reconciled to the device inventory. This gap is examined again as the worked example in the evidence-judgment section below.

Gap 7 · Old policy document (a trap: age is context, not a defect)

The pack included a policy document with an old effective date. The trap is to flag "old = out of date = gap." Age alone is not a finding.

What a strong write-up contained: the reasoning that an old document is not automatically a gap when its annual-review clause is appropriate and the review has actually been performed. The correct move is to record the document's age as evidence context, then check the substantive question: does the policy require periodic review, and is there evidence the last review happened on schedule? If the review clause is sound and reviews are occurring, there is no gap; if the clause is missing or the reviews lapsed, that is the gap, not the age. Flagging the document purely for being old lost marks; reasoning about the review clause earned them.

Where people went wrong on the seven

The most common failure was flagging all seven as gaps to look thorough, which meant failing both traps (Gap 5 and Gap 7). The second was under-analysing Gap 3: naming BYOD as a gap but keeping the planted data-loss mapping and never mentioning privacy, notice, or proportionality. The third was accepting Gap 6's screenshot as proof of encryption. Precision beat coverage here.

3.3Control mapping in depth

A mapping is a promise about what a control must enforce, not a label. The pattern that scored well was: gap, then control family, then the concrete requirement the control has to check and evidence. Below is a small illustrative crosswalk. The control families are fictional-but-representative names used for teaching; use your assigned control identifiers in your own work.

The pack's own mapping pointed only at a data-loss control, which addresses data leaving the device but says nothing about whether the organisation may lawfully and proportionately inspect a personal device in the first place. The mapping that earned marks reassigned the primary control to privacy and personal-data protection and kept the data-loss control as a secondary, supporting control rather than the justification.

3.4Evidence judgment in depth

Every artifact in the pack needed a verdict, and every verdict needed to separate three things: what you literally observed, how you interpreted it, and what rubric-relevant conclusion it can and cannot support. The discipline is to state a confidence level and to consider the alternative reading before you reject it. Here is the stale device screenshot worked all the way through, because it is the artifact that most tempted people into over-claiming.

Worked example: the stale device-management screenshot

Observed fact. An image dated in a past period shows a management console reporting 91 managed devices, of which 89 report disk encryption enabled. The image carries no export metadata: no verifiable generation date, no query, and no statement of what population it covered.

Interpretation. At some past moment, most of a then-managed subset appeared encrypted. But the current inventory is 176 devices plus an unknown number of personal devices. So the screenshot describes roughly half of today's estate at best, at an unknown past date, and even within its own subset it shows two unencrypted devices.

Verdict. Low-confidence historical evidence for a subset. Rejected as proof of current, universal encryption. It can support a much weaker claim ("encryption was largely deployed to the managed subset at some past point") but not the compliance claim the pack invited.

Alternative considered and rejected. One could argue "89 of 91 is 98 percent, so the estate is essentially encrypted." Rejected, because the denominator is wrong (91 is not 176), the date is stale, personal devices are entirely absent from the count, and with no export metadata the scope of even the 91 is unverifiable. To prove current compliance you would need a current, dated, full-population export reconciled to the device inventory.

Apply the same three-part structure to every artifact: the MFA screenshot proves a few accounts, not a rule; the old policy proves an effective date, not a lapsed review; a ticket proves a request, not an outcome. Confidence lives in the gap between observation and conclusion, and your marks lived there too.

3.5The exactly-three machine controls

You implemented exactly three controls in Rego, evaluated by Open Policy Agent. No fourth control, and you must not replace an assigned one with a substitute of your own choosing. The three were:

  1. NF.IDENTITY.PRIVILEGED_ASSURANCE: privileged identities must have a valid owner, phishing-resistant MFA, and fresh credentials.
  2. NF.STORAGE.RESTRICTED_PROTECTION: restricted data stores must be non-public, encrypted, and logging access.
  3. NF.ENDPOINT.MANAGED_HEALTH: endpoints must be managed, disk-encrypted, running healthy endpoint protection, and not stale.

Every decision your policy emitted had to carry all five of these fields, and the policy had to default to deny: an asset that does not affirmatively satisfy the control is denied, not silently allowed.

FieldMeaning
policy_idWhich of the three controls produced this decision.
asset_locatorWhich specific asset from your assigned state the decision is about.

violation_codeWhich violation family was triggered on a deny (empty or none on an allow).
evidence_locatorWhere in your state the fact that drove the decision can be found.

Exception validation

Real compliance allows for approved, temporary exceptions, so your policy had to handle them without becoming a backdoor. A valid exception needed all five of: an owner accountable for it, a reason, a recorded approval, an expiry date, and a compensating control that reduces the risk in the meantime. If any of those were missing the exception is incomplete; if it was structurally broken it is malformed; if the expiry has passed it is expired. In every one of those cases the correct behaviour is to deny and emit EXCEPTION_INCOMPLETE or EXCEPTION_EXPIRED. An exception is a documented, owned, time-boxed acceptance of risk, never an "allow anyway" flag.

The rule that decided most GRC scores

The Rego had to evaluate the actual state of your assigned inputs. It must not embed asset ids, must not depend on the ordering of the input fixtures, and must not contain copied expected results. If your policy would produce the right ledger only because the answers were baked into the code, it evaluated nothing and earned nothing for the decision criterion. Concretely, the policy had to pass opa check (it parses and compiles) and opa test (its tests pass), with the Rego language mode declared and consistent. Mixing an older test syntax against a newer policy syntax, or the reverse, meant the bundle did not run as submitted, and a bundle that does not run cannot earn decision marks no matter how correct it looks on paper.

Below is a small, deliberately fictional, illustration of the shape of a deny decision. It is not copied from any candidate or fixture; it exists only to show the five required fields flowing out of an evaluated fact. Your real policy would derive every value from your own input, never from literals like these.

# ILLUSTRATIVE ONLY - shape, not a copyable answer.
# Endpoint control: deny by default, allow only if fully healthy.
package grc.compliance

default endpoint_allow := false

# an asset is allowed only when EVERY health fact holds
endpoint_allow if {
  some d in input.endpoints
  d.managed == true
  d.disk_encrypted == true
  d.edr_healthy == true
  d.last_seen_days <= input.policy.max_stale_days
}

# emit a full decision per endpoint, defaulting to deny
decisions contains decision if {
  some d in input.endpoints
  not d.disk_encrypted
  decision := {
    "policy_id":        "NF.ENDPOINT.MANAGED_HEALTH",
    "asset_locator":    d.locator,          # from state, not a literal id
    "decision":         "deny",
    "violation_code":   "ENDPOINT_DISK_UNENCRYPTED",
    "evidence_locator": d.evidence_ref,      # points back into your input
  }
}

The teaching point is not the exact syntax; it is that asset_locator and evidence_locator come out of the input, the decision follows from a fact in the state (not d.disk_encrypted), and the default is deny. A policy written that way produces the right ledger for whatever state it is handed, which is exactly what the private fixtures test.

3.6Enforceable drafting

The addendum was where governance met accountability. Every clause had to be something a person could be held to and a reviewer could check. Six elements made a clause enforceable: an owner (a named, accountable role), a scope (who and what it applies to), a requirement (the concrete, testable obligation), an exception route (how to request a time-boxed, compensated exception), enforcement evidence (what artifact proves the clause is being met), and a review cadence (when the clause itself is re-examined). A clause missing any of these was aspirational, and aspiration is not enforceable.

Illustrative clause skeleton (fictional)

Clause: privileged access requires phishing-resistant MFA.

  • Owner: Head of Identity.
  • Scope: every privileged identity across production systems, including break-glass and admin service accounts.
  • Requirement: privileged authentication must use a phishing-resistant factor; access without it is denied.
  • Exception route: request via the exception register with owner, reason, approval, expiry, and a compensating control; expired or incomplete exceptions deny automatically.
  • Enforcement evidence: the identity control's decision ledger showing allow or deny per privileged identity, retained.
  • Review cadence: reviewed quarterly, and on any material change to the identity platform.

Note how the enforcement-evidence line ties the written clause back to the machine control from section 3.5. That is the join the strongest submissions made: the policy said what must be true, and the running control proved it per asset. A polished addendum with no working controls behind it could not pass the technical assessment; the words and the code had to agree.

3.7Reproduce it yourself

Everything in this track is checkable on your own machine. Load your assigned state, never an invented scenario, and run the following. The last two steps are the ones that prove your policy evaluates state rather than memorising answers.

# 1. preserve the supplied input hashes; work from YOUR assigned state
# 2. confirm the bundle parses and compiles
opa check policy-bundle/

# 3. run your tests with the declared language mode; do not mix versions
opa test policy-bundle/ -v

# 4. produce the decision ledger from your own input state
opa eval --format=json \
  --data policy-bundle/ \
  --input input/control-state.json \
  'data.grc.compliance.decisions'

# 5. THE STATE TEST: change one asset id and reorder the input array
#    then re-run step 4 against the edited input
# decisions must follow the changed facts, and each asset's decision
# must be unchanged by mere reordering. if a decision moves because you
# renamed an id or shuffled the list, the policy is not evaluating state.

# 6. reconcile the whole submission so it tells one story:
#    policy  <-> tests  <-> decision ledger  <-> evidence index
#    <-> addendum clauses  <-> residual-risk deferrals

Step 5 is the exact spirit of the private fixtures staff ran: the same policy, handed a different state, must yield the decisions that state deserves. Every material risk you did not turn into a machine control still needed a disposition in your deferrals (defer, accept, transfer, or reduce through an existing control), each with an owner, a rationale, any dependency, and a review trigger. The private fixture ids were never expected in your files; staff supply and run those.

3.8Where people went wrong

The three failures that cost the most

  • A beautiful document with no controls. Some submissions were genuinely well written: clear gaps, thoughtful mappings, a polished addendum, and no running Rego, or Rego that was really just prose in a code block. The drafting criterion is only 15 of 100, and the decision criterion (20) plus much of mapping and evidence depend on controls that actually run. Words alone could not pass this project's technical bar.
  • Rego that did not run, or mixed language versions. Bundles that failed opa check, contained invalid inline logic, defaulted to allow instead of deny, or paired old-syntax tests with new-syntax policies did not run as submitted. A control that does not execute proves nothing about your assets, so the decision marks could not be awarded however plausible the code looked.
  • Analysing an invented scenario instead of the assigned inputs. Some candidates described a generic company and wrote generic controls, never touching the specific state they were given. Because the policy has to evaluate your assigned state, work aimed at an imagined scenario could not be reconciled to the fixtures and earned little, even when the general reasoning was sound.

  • Record an evidence verdict for every artifact: observed fact, interpretation, verdict, alternative rejected.
  • Reject the stale device screenshot as proof of current universal encryption; state what real proof would be.
